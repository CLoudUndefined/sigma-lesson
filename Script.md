#### Контейнеры (техническая часть, для заметки себе)

Учеников точно будет 18. Готовим 18 Docker-контейнеров заранее (не on-demand), потому что все равно не все ученики придут.

Каждый контейнер - отдельный порт на хосте, проброшенный внутрь (docker -p 220X:22). Надежнее, чем прыжок по логину через ForceCommand/PAM на хосте - это стандартный Docker-паттерн, без магии на хосте. Из минусов - надо не забыть на первой паре в водной части рассказать и показать про `-p` флаг, а то кто-то попробует зайти обычным ssh login@ip и не поймет, почему не пускает.

Бот выдает пачкой: логин, пароль, порт.

Смена prompt (решено): signed при успешной проверке создает файл-маркер .signed-complete в домашней папке. .bashrc проверяет существование файла при каждом новом шелле - если есть, переопределяет PS1 на:
```

(Pre-junior) login@server:~$
```

чтобы закрепить, что теперь ученик крутооооой. Можно будет менять статус ученика каждую пару

учитываем, что ошибки всегда должны быть объяснены и направляющими, а не случайными!

Структура домашней папки (решено): генерируется разная на каждый контейнер. Тематические папки (hr_department/, trash/, server_configs/ и т.д.) - одинаковые на всех, но внутренняя структура (куда именно попадает каждый из файлов, и на какую глубину) - случайная.

Глубина: до 4 уровней, но не все ветки обязаны идти до конца - где-то файл может лежать на 2 уровне, где-то на 4.

Мусорные файлы для антуража (cat-memes.jpg, my_tears.txt и т.д.) - беру из заранее подготовленной папки-пула, генератор растягивает их по дереву для правдоподобия.

Для облегчения тем, кто не найдет - ставим в контейнер tree, чтобы вывести дерево папок и найти нужный код.

contract.txt - не дублировать (в прошлой версии случайно был в двух местах, это баг черновика, не задумка).

Dot-files/dot-dirs (решено - опционально, не часть основной программы): откладываем как гроб-задание. Используем в двух случаях - если пара идет быстрее ожидаемого и нужно чем-то занять время, или конкретному ученику, который мешает/торопит пару, выдаем усложненный вариант без объяснений - сам разбирайся с ls -la и скрытыми файлами.

Особый код в dot-файле дает другой результат через signed: другой файл (не обычный my_id.txt) и другой prompt - вместо (Pre-junior) выдает:
```

(Beagle-junior) login@server:~$
```
(намек на будущую роль "ищейки" в занятии 3, для тех, кто нашел раньше времени)

### Занятие 2: Демиург (несчастный)
Цель: Научиться управлять файловой системой (mkdir, cp, mv, nano).
Суть: Собираем сайт из мусора и объедков. cp - на примере sites-available/sites-enabled для nginx (оригинал конфига оставляем на месте, копию кладем в enabled).

#### Заход и новая записка (cat)
На прошлом занятии мы подписали договор (не контракт!) и научились ориентироваться в папках сервера. Сегодня мы начинаем новую работу. Володя оставил новую записку:

#### Далее! Мы осматриваем места происшествия (ls, cd)
Проверяем, правду ли говорит Володя.

Сайта нет. Допустим. А что в той мусорной папке?

ls ~/seo_mess - видим index.html, папку assets (картинки) и мусор (cat-memes.jpg, my_tears.txt, deathconsciousness.mp3 и т.д.), **может еще какие-то папки**.

Нам нужно перенести только нужное на законное место.

#### Работа грузчика, насяльнике (mkdir, mv, cp)
Сначала создадим папку для сайта (если рассмотрим такой сценарий)

sudo mkdir -p /var/www/demo *(впервые знакомимся с sudo: "Насяльнике Володя дал нам права строителя")*

Теперь переносим index.html

sudo mv ~/seo_mess/index.html /var/www/demo/

С папкой assets то же самое.

sudo mv ~/seo_mess/assets /var/www/demo/

Проверяем, что все на месте: ls /var/www/demo. Есть? Отлично.

#### Пробуем открыть сайт - облом (nginx)
Идем в браузер, открываем сайт... а он не открывается. Ошибка nginx (502 / connection refused).

"Так, файлы на месте, а сайт не открывается. Значит дело не в файлах сайта, а в том, как nginx вообще о них узнает."

Смотрим в sites-available/demo.conf (уже лежит в штатном месте, не в seo_mess - это отдельный, обычный файл конфигурации).

sudo nano /etc/nginx/sites-available/demo.conf

Видим, что root указывает куда-то не туда: root /seo/rock/sysadmin/sucks/ (еще один привет от психанувшего SEO-шника). Поправляем на правильный путь: root /var/www/demo;

Показываем, как сохранить: Ctrl+O, Enter, Ctrl+X

"Прежде чем включать конфиг - хорошая практика сначала проверить, не накосячили ли мы сами."

sudo nginx -t - проверка синтаксиса конфига. Видим "syntax is ok / test is successful".

"Теперь копируем (не переносим!) конфиг в sites-enabled - там nginx ищет активные сайты. Оригинал в sites-available оставляем как есть, мало ли пригодится."

sudo cp /etc/nginx/sites-available/demo.conf /etc/nginx/sites-enabled/demo.conf

Осталось заставить nginx перечитать конфиги. Мы в контейнере, systemd тут скорее всего нет, так что не systemctl, а напрямую:

sudo nginx -s reload

Обновляем браузер - сайт открывается!

Посмотрим, что может сделать еще папки/файлы. Но не думаю, самое основное - просто научить что-то создавать и перемещать.

### Занятие 3: Ищейка
Цель: Поиск секретов, анализ логов.
Суть: Использование команд для чтения и фильтрации текста (cat, grep, head, tail, pipe).

#### Заход
"На прошлом занятии мы поработали на сервере, немного дополнили свои сайты и научились ориентироваться через терминал. Сегодня утром я захожу, проверяю что да как - а сайт не работает. Старший администратор Володя прислал папку с логами и записку, объяснил кратко ситуацию, а потом ушёл на конференцию. Как жалко. Справимся и без него - давайте разберёмся что произошло!"

Открываем терминал. Видим что мы в домашней папке. Делаем ls - видим папку sysadmin. Заходим через cd sysadmin, снова ls - смотрим что внутри.

#### cat - читаем улики
"О, Володя таки нам что-то оставил. Почитаем."

cat note.txt

Содержимое записки: "Ночью был подозрительный вход. Кажется к нам снова завалился тот тип, который кошмарит наш сервер запросами уже вторую неделю. Я собрал список странных IP в scammer.txt - проверь, может кто-то из них таки смог пробраться. Удачи тебе, подаван."

cat scammer.txt - список IP, среди них 77.88.44.242. Запоминаем его.

"Уже знаем кого искать. Идём в логи."

#### head/tail - смотрим что было
cat access.log - поток строк не останавливается.

"Ох... давайте посмотрим сколько тут строк."

wc -l access.log - "20 000 строк. Мы конечно можем читать всё это... но сервер уже упал, времени нет. Нас интересует что было прямо перед падением - это последние записи."

tail -n 30 access.log - видим подозрительную активность нашего IP в конце.

"Вот он. Видим когда зашёл и что делал перед тем как сервер упал. Но нам нужны все его следы - не только последние."

#### grep и pipe - ищем все следы
grep "77.88.44.242" access.log - все запросы с этого IP по всему логу.

"Много всего. Видим что он явно интересовался nginx - а там же наши конфиги для сайта! Давайте отфильтруем ещё раз, только по nginx."

grep "77.88.44.242" access.log | grep "nginx"

"Pipe - ее можно представить у себя в голове как конвейерная лента на заводе. Одна машина (команда) отобрала нужные детали, передала по ленте второй, та отгравировала, передала третьей - та покрасила. Здесь то же самое: первый grep отобрал строки с нашим IP, передал второму, тот оставил только строки про nginx."

Среди результатов видна строка где он обращался к /tmp/.hidden-secret/ - подсказка где спрятан конфиг.

"Есть! Он что-то переместил в /tmp/.hidden-secret/. Давайте проверим."

ls /tmp/.hidden-secret/ - видим nginx.conf.

cat /tmp/.hidden-secret/nginx.conf - вот он, наш конфиг.

#### Финал - чиним и отчитываемся
"Нашли. Теперь вернём конфиг на законное место - он должен лежать в /etc/nginx/sites-enabled/."

sudo mv /tmp/.hidden-secret/nginx.conf /etc/nginx/sites-enabled/

"Конфиг на месте, но nginx о нём пока не знает - надо, как и в прошлый раз, перечитать конфиги."

sudo nginx -s reload

"И оставим Володе отчёт - что нашли, кто виноват."

grep "77.88.44.242" access.log > report.txt

"Вот и всё. > - это как сохранить результат в файл. Всё что grep нашёл - теперь лежит в report.txt, Володя вернётся с конференции и увидит, что он нам не так уж и сильно нужен."

"Это и есть работа ищейки - не читать 20 000-40 000 строк подряд, а знать как быстро найти нужное и исправить то что в наших силах. А сайт - проверяем."

Открываем браузер, сайт работает. (Тима-Момент для "УНГА БУНГА" дурачка, махая руками)

#### Гроб-задание (для опережающих, мешающих или торопящих)
Взломщик оставил не только след в логах - в файловой системе спрятан второй, более скрытный след, который не виден через grep.

Где-то в домашней папке ученика лежит символическая ссылка (симлинк) на настоящий .py-файл, спрятанный отдельно. Сам .py-файл: владелец может его читать (без искусственных тупиков с sudo), права в целом выглядят нетипично на фоне обычных файлов. Внутри - вызов os.system(...), явный признак подозрительного скрипта.

Ищем симлинк: find ~ -type l (ограничено домашней папкой - быстро и безопасно, в отличие от find / по всей системе).

Находим ссылку, смотрим ls -l - видно, куда она указывает (-> /путь/к/файлу).

Идем по пути, cat - видим os.system(...).

Переносим найденный файл в отдельную папку-хранилище улик (по аналогии с nginx.conf в основном занятии).

#### Магия архивации дедов (tar)
Копировать папку целиком - долго, и она занимает много места. Можно использовать архивы! Это как rar, только быстрее и мощнее.

Создаем папку

mkdir ~/backups

Запускаем архивацию вручную:
tar -czvf ~/backups/site_backup.tar.gz /var/www/demo/

(На экране пролетает красивая стена текста с упакованными файлами. Параллельно объясняем странный набор букв czvf).

Одна команда, и весь сайт сжат в один файл. Но... каждый день писать эту команду (хреновину) руками мы не будем. Я лентяй, ты лентяй, все мы лентяи

#### Пишем сценарий Воронинов (nano, bash)
Скрипт - это когда мы записываем команды в файл, чтобы сервер выполнял их за нас, последовательно.

nano ~/backup.sh

Пишем:

```bash
#!/bin/bash
DATE=$(date +%Y-%m-%d_%H-%M)
echo "Начинаю упаковку сайта..."
tar -czvf ~/backups/site_$DATE.tar.gz /var/www/demo/
echo "Бэкап успешно сохранен!"
```

Переменная DATE нужна, чтобы каждый бэкап имел уникальное имя, иначе они будут перезаписывать друг друга.

Запускаем: bash ~/backup.sh
Проверяем: ls ~/backups - видим архив с датой!

#### А место на диске не бесконечное (cleanup.sh)
Личная история (моя): рассказываю, как у меня самого закончилось место в облаке с бэкапами, и я потерял кучу работы из-за этого. Бэкапы копятся, диск не резиновый - надо и убирать за собой.

Пишем второй скрипт-компаньон:

nano ~/cleanup.sh

```bash
#!/bin/bash
OLDEST=$(ls -t ~/backups | tail -n 1)
rm "~/backups/$OLDEST"
echo "Удалили старый бэкап: $OLDEST"
```

ls -t - сортирует файлы по времени изменения (новые сверху). tail -n 1 - берет самый последний из списка, то есть самый старый бэкап. Обе команды уже знакомы с прошлого занятия - просто новая комбинация.

Запускаем: bash ~/cleanup.sh
Проверяем: ls ~/backups - самого старого архива больше нет.

#### Замок на амбаре (chattr)
Но погодите. А что если кто-то (или мы сами, как Володя в этой истории) случайно наберет rm -rf прямо в папке ~/backups? Все бэкапы одним махом исчезнут - и тогда план Б сам станет жертвой той же беды, от которой должен был спасать.

Хранение бэкапов на той же машине - не бэкапы, а невесть что. Но так как мы не обладаем датацентром (мы ведь бедные и нищие студенты), давайте обезопасим папку с бэкапами от удаления и записи лишний раз - при помощи chattr! Будем снимать замок с амбара при удалении бэкапов и записи новых, и закрывать обратно, когда закончили.

Тут впервые за занятие понадобится sudo - chattr трогает не просто права на файл, а особый системный флаг неизменяемости, и обычному пользователю такое не положено. Как и в занятии 2 - права строителя от Володи.

Дописываем оба скрипта, добавляя снятие и установку замка вокруг основного действия:

```bash
#!/bin/bash
DATE=$(date +%Y-%m-%d_%H-%M)
echo "Снимаем замок с амбара..."
sudo chattr -i ~/backups
echo "Начинаю упаковку сайта..."
tar -czvf ~/backups/site_$DATE.tar.gz /var/www/demo/
echo "Закрываем замок обратно..."
sudo chattr +i ~/backups
echo "Бэкап успешно сохранен!"
```

```bash
#!/bin/bash
echo "Снимаем замок с амбара..."
sudo chattr -i ~/backups
OLDEST=$(ls -t ~/backups | tail -n 1)
rm "~/backups/$OLDEST"
echo "Удалили старый бэкап: $OLDEST"
echo "Закрываем замок обратно..."
sudo chattr +i ~/backups
```

Проверяем: пробуем rm -rf ~/backups/* пока замок стоит - не выходит, "Operation not permitted". Замок держит.

#### Сбор данных (df -h, >>)
Давайте подумаем, как отправить текст из терминала прямо на наш сайт.

Мы уже знаем знак >. Но он стирает всё. Оператор >> - дописывает в конец.

Как узнать место на диске? ===> df -h /

#### Создаем Лже-Дашборд (nano)
Давайте напишем скрипт, который создаст страницу.

nano ~/status.sh

Пишем:

```bash
#!/bin/bash
# Создаем файл сайта (перезаписываем старый >)
echo "=== СТАТУС НА $(date) ===" > /var/www/demo/dashboard.txt
echo "" >> /var/www/demo/dashboard.txt
echo "Место на диске:" >> /var/www/demo/dashboard.txt
df -h / >> /var/www/demo/dashboard.txt
echo "" >> /var/www/demo/dashboard.txt
echo "Оперативная память:" >> /var/www/demo/dashboard.txt
free -h >> /var/www/demo/dashboard.txt
echo "" >> /var/www/demo/dashboard.txt
echo "Последние бэкапы:" >> /var/www/demo/dashboard.txt
ls -l ~/backups | tail -n 3 >> /var/www/demo/dashboard.txt

echo "Отчет готов. Все свободны" >> /var/www/demo/dashboard.txt
```

Запускаем руками: bash ~/status.sh.

А теперь идите в браузер: http://<ip-сервера>:8080/dashboard.txt.

Ученики видят реальные серверные данные прямо в интернете. Отлично.

#### Оживление Франкенштейна (crontab)
Но если вы сейчас обновите браузер, время не изменится. Скрипт надо запускать. Заставим сервер делать это без нас.

Открываем расписание: `crontab -e`

Добавляем в конец файла две строчки (звездочки объясняем как "каждую минуту", **стоит объяснить синтаксис и как это настраивается**):

```bash
# Обновлять статус каждую минуту
* * * * * bash /home/student/status.sh
# Делать бэкап каждые 5 минут
*/5 * * * * bash /home/student/backup.sh
# Убирать старые бэкапы раз в 20 минут (реже backup.sh, чтобы бэкапы успевали накопиться)
*/20 * * * * bash /home/student/cleanup.sh
```

Сохраняем и выходим.

#### Про периодичность backup.sh и cleanup.sh (важно учесть при настройке)
Учесть при подготовке занятия: раз теперь два скрипта, периодичность в crontab у них разная не просто так - если cleanup.sh запускать так же часто, как backup.sh, бэкапы не успеют накопиться. Подобрать конкретные интервалы под тайминг занятия, чтобы ученики успели увидеть эффект от обоих скриптов за урок.
